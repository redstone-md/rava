**rava v0.0.2-alpha: a modded Minecraft server now ticks faster than on HotSpot.**

`alpha` · Linux, macOS and Windows on x86-64 · Java 21 class library · drop-in `java`

> [!WARNING]
> An alpha: expect crashes and differences from HotSpot, and keep backups of any world you open
> with it. Reports are welcome in [Issues](https://github.com/redstone-md/rava/issues).

The headline of this release is the All The Mods 10 server tick. On the same host, in
alternating rounds with a fresh world each, the NeoForge server runs its tick sprints about 10%
faster on rava than on HotSpot 21 and uses about a quarter less CPU. Before the work in this
release it was 12-18% slower. Starts are still cold: no class-data archive, no
checkpoint/restore, no AOT cache, and nothing is tuned for Minecraft.

## Performance

All The Mods 10, NeoForge 1.21.1, a fixed mob scenario, i5-14400F with both VMs pinned to the
performance cores, JDK 21:

| Format | rava | HotSpot 21 |
|---|---:|---:|
| 3 rounds of three 2000-tick sprints | **26.2 ms/tick** | 29.0 ms/tick |
| 4 rounds of two 4000-tick sprints | **27.4 ms/tick** | 28.9 ms/tick |

rava was ahead in every round of both. Round-to-round spread on that host is about 1.5 ms,
so only interleaved rounds compare.

Most of the gap closed in a few places that a per-instruction profile showed:

- Interface type checks (`instanceof`, `checkcast`) probe a per-class hash set of the class's
  interfaces. Before, every "no" answer scanned all of them, and modded entity classes have
  dozens. This alone took the tick from 31.1 to 27.6 ms.
- Megamorphic interface calls find the implementing block the same way instead of scanning
  the itable (2.7× faster than before on a call-heavy benchmark, 2.5× faster than HotSpot).
- Behind a class guard, an inlined method's calls on `this` bind statically even when the
  receiver is a merge of values. Profiles of interface default methods are shared by every
  implementation (world generation fills them with other chunk classes), and a block collision
  loop was paying an interface call per block.
- Optimization starts after 2500 invocations and inlines to C2's budgets; private interface
  methods bind statically; Latin-1 string equality is compared inline; switches compile to
  jump tables or binary search; merges of fresh objects scalar-replace.
- Register saves around calls follow block liveness, branches thread through jumps, and
  `instanceof` of a class is one compare against the class display.

## Memory

- `-Xmx` bounds the heap as HotSpot's does.
- Young collections promote small objects depth first into mixed old pages, and full
  collections empty mixed pages up to 75% live, so long-lived data sits closer together.
- On Windows, discarded heap ranges give their commit charge back and mimalloc commits page
  memory on demand.

## Also new

- `-Drava.opengl=vulkan` renders the Minecraft client through the bundled Zink (Mesa's OpenGL
  on Vulkan) on Windows.
- Diagnostics: `RAVA_SAMPLE_STACK=1` writes folded Java stacks (inlined frames included) for
  comparison with a JFR recording; `RAVA_SAMPLE_DETAIL=/` counts every compiled method per
  instruction with the instruction's bytes; `RAVA_GC_WHY=<class>` names the roots holding a
  class's objects; `RAVA_NATIVE_PROF` samples the VM's live native allocations.
- Thread dumps that ask for locked monitors work.

## Known limits

- x86-64 only, and the Java 21 class library only.
- Server start is still slower than HotSpot's (about 1.2× on Paper 1.21), mostly world
  generation.
- rava does not produce helpful `NullPointerException` messages yet.
- Some programs will crash or behave differently from HotSpot. Please report them with
  `rava -version`, the system, the command line and the full output.
