# ROUND 2 — two corrections that rewrite this file's own conclusions

Full tables: `docs/rip-profile-2026-07-27.md`. Both corrections come from RIP sampling the windows
that had never been RIP-sampled, and both invalidate statements made above.

## ⛔ 1. The ring is NOT "pure compiled-code throughput"

This file records the ring as "97.1% JIT_EXEC, 1.4% dispatch, 0.6% native bridges". That is the
WALL sampler's row — the artifact this very file documents (the guard wraps all of `jit_run`, so
host callbacks bill to JIT_EXEC). **The correction was applied to Block B in round 1 and never to
the ring.** RIP says the ring is **37.0% inside compiled code, 63.0% host**, and its single largest
host block is the **dispatch host path at 29.9% self-time**.

This retro-explains the entire ring arc: the memo lever (`hits=0`) and the parallel lever (+37%)
both aimed at compiled-side work that is only a third of the window, while `REF_STATIC_CELLS` —
which removed a HOST CALLBACK CLUSTER — is the one that moved it −31%. Third confirmation of the
same rule.

## ⛔ 2. The serial residue COLLAPSED, 11.2s → 2.2s — so the impossibility proof is VOID

Measured identically in both boots (2.25s / 2.26s). The residue is now **3.2% of the Done window,
not 11%**; the ring is **96.8%**. Consequences for claims made above:

* **"`Done ≤ 10s` is unreachable IN PRINCIPLE" no longer holds on these numbers.** The arithmetic
  was `11.2 + 92.6/12 = 18.9s`; it is now **`2.2 + 67.8/12 = 7.9s`**, and ~2.2s at infinite cores.
  Ring parallelism is still REFUTED *on measurement* (+37%), so this retires the impossibility
  ARGUMENT, not the refutation — but the goal can no longer be dismissed as arithmetically closed.
* **"A lever on the DensityFunction/Climate object graph hits ~100% of the window"** is now worth
  far less: the graph BUILD is 3%, the EVALUATION is 97%.
* The residue window at n=158 samples is too small to rank — read it as a shape, not a top-15.

## The biggest single named lever now open: 14% of the ring is a field-name lookup

One proven chain owns it, and it is the only chain under `resolve_field_id` in the whole window
(396/396 samples): `resolve_field_id < fu_double_view < jit_fu_invoke < rava_fu_invoke`.

`PerlinNoise.getValue` reads `this.amplitudes.getDouble(i)` once per octave; `amplitudes` is a
fastutil `DoubleImmutableList`, so the call lands in `fu_double_view` (`lib.rs:11799`) which does
**on every call** `resolve_field_id(owner, "a")` (and `"size"` for array lists) — a thread-local
memo whose HIT still costs a `LocalKey::with` plus a hash of a 44-character class name. That is why
`LocalKey::with` is the ring's **#2 leaf at 8.9%**, with 68% of its proven consumers being
`resolve_field_id`. Totals: `rava_fu_invoke` 14.0% inclusive, `fu_double_view` 10.0%,
`resolve_field_id` 6.7% of which the TLS+hash is 6.3% of the window.

The fix is the shape already applied ~30 lines away: `fu_iter_field_ids` (`lib.rs:11826`) memoises
`($elems,$pos)` in a `OnceLock` for exactly this reason. `fu_double_view` was never given it. Note
two owners exist (`DoubleImmutableList`, `DoubleArrayList`), so a bare `OnceLock` pair is not enough.

## What transfers to the boot, and what does not

The single most useful rule found in these two days:

| change | microbench | real boot |
|---|---|---|
| COW guard diamond unswitched to method entry | 3.16× | **−2.1%** |
| 24 → 16 byte object header | BigGraph −4.5%, −8 MiB | **−6.3%, −68 MiB** (shipped default) |
| lambda impl-key (site address vs FNV fold) | ChunkFill SETUP −15.7% | **+1.0%** |
| arena-receiver method-entry unswitch | body 445 → 321 instrs | **+11.3%** |
| `String.charAt` JIT intrinsic | StrScan **9.6×**, 2,013,670 → **0** bridge calls | **no measurable block-C win** |

**Cheapening an OPERATION transfers. DUPLICATING a BODY does not.** The boot compiles ~1140
bodies and runs much of that code briefly, so unswitching and inlining pay for compilation and
i-cache without amortising. Any body-duplicating optimisation needs a hotness gate before it is
considered again.

Corollary about proxies: a ChunkFill win does not transfer either. The sharpest case is the
lambda impl-key — a profiling pass had established that ChunkFill's SETUP phase *is*
`Bootstrap.bootStrap()` **by code composition**, and the win still did not carry. The phases
match in WHAT they execute but not in the PROPORTIONS. Use ChunkFill as a correctness gate
(hash `8790f04ace726ecf`) and a direction-finder; take the number from an interleaved full boot.

## The bridge census OVERSTATES what removing a bridge buys — 2026-07-26

`RAVA_BRIDGE_STAT` priced `String#charAt` in block C at **2,013,670 calls / 1.81s**, which reads
as a 1.8-second lever. The `charAt` JIT intrinsic then removed **100%** of those calls — the
entry disappears from the census entirely — and **block C did not move**: 31245 ms before the
change, 31298 ms after, on the same box minutes apart. Twelve further interleaved A/B runs
(`bench/wt_blockc_ab.ps1`, both orderings) put the effect inside the noise: the intrinsic-on arm
spans 26.6-32.6s and the intrinsic-off arm 28.2-59.1s, so the ~1.8s being chased is a fraction of
the run-to-run spread on the step itself.

Two things follow, and both are about method rather than about `charAt`:

1. **A census self-time is an upper bound on the lever, not its value.** The tally wraps every
   bridge in two `Instant::now()` calls and a mutex-guarded map update, so a bridge's cost scales
   with its CALL COUNT independently of its work. Rank by count × work, and confirm any
   high-count/low-work candidate against an uninstrumented wall before budgeting for it.
2. **This box cannot currently resolve a 2s effect on a 27s step.** In the same twelve runs
   `Bootstrap.bootStrap` ranged **52.9-119.7s** — a 2.3× spread under P-core affinity and the
   High-Performance plan, the same signature as the older E-core-hop/freq-scaling finding. Any
   result under ~10% on block C needs many more pairs than three, or a quieter machine.

The counts themselves stay trustworthy — they are exact and instrumentation-independent, which is
what makes them the right evidence for a coverage or dispatch-shape claim (see the owner-chain
retry below), just not for a wall claim.

**This converges with the day's other repricing, reached from a different direction.** A warm host
fall costs ~99 ns (measured by removing 1.41M of them for 2.3%), so 2,013,670 `charAt` calls are
worth **~0.2s, not 1.81s**. Two independent measurements, one conclusion — the gap between billed
and real is the instrumentation.

The sharper form of the rule: billing ≈ `real_work + N × instrumentation`, so **trust the census
when N is small and the work per call is large; distrust it when N is huge and the work is
trivial.** That is exactly why the composite-comparator key cache DID transfer (−8.5%: `ArrayList#sort`
is few calls, much work) while `charAt` did not. Rank bridge targets by work per call, never by
billed total.

## The instrumentation gap — CLOSED 2026-07-26

Per-method attribution now exists in `rava_sampler`, hooked at the `jit_method_push/pop` pair
already bracketing `call_raw` in `jit_run` (`lib.rs:9863`) — the only site that already fenced
every VM→machine-code entry, so nothing was added to compiled bodies. Identity is an interned
`u32` on `JitFn.mid`. It also made the UNGATED path cheaper: `jit_method_push(format!(...))` ran
unconditionally on every compiled entry — 5,058,495 entries per ChunkFill run across 11,031
methods — and is now 11,031 formats (459× fewer).

⚠ **Read the units carefully.** The cost A/B for that change ran while other agents were
benchmarking on the same P-core mask, so its **−1.9% median does not survive**; what survives is
"no regression, direction favourable" (interleaved, instrumented faster in 3/3, and the mechanism
is a removed allocation). By the same token the **tick SHARES below are sound but the SECONDS are
not**: contention stretches wall clock without reweighting which method owns a sample, so
`initCache` at 37.8% holds while its "18.8s" inherits an inflated wall.

Two structural facts came out of it:

* Attribution is **entry self-time**. PIC and direct-mono hits jump to the callee with no Rust
  frame, so a fully PIC-resolved subtree bills to the frame that entered it.
* **ChunkFill's FILL phase is one row**: `ChunkFill.main` is 1621 of 1622 ticks (99.9%). That is a
  verdict, not missing data — the density tree is PIC-called from compiled `main` and never
  re-enters Rust, so FILL cannot be decomposed without emitting into compiled bodies, which the
  transfer rule above forbids.

## The JIT_EXEC row is NOT compiled code — corrected 2026-07-26

There was a third route, and it closes the gap above without emitting anything: **sample the
guest thread's instruction pointer** (`RAVA_PROFILE_PC`, `diagnostics.pc_profile`). The sampler
thread suspends the guest, reads RIP, resumes, and maps the address at dump time to the compiled
function whose code range contains it — or, via the PDB, to the Rust host function. Codegen is
byte-identical with the flag on or off, so the transfer-rule objection does not apply.

It says the JIT_EXEC row has been read backwards. **Inside compiled code: ShapeOr 6.5-7.4%, the
real boot 3-16% (Block B 5.7%).** The rest is the Rust host. `rava_sampler` raises its JIT_EXEC
guard around the whole of `jit_run`, so every callback from compiled code back into Rust that
does not itself raise a category — the dispatch host path, the arena/field helpers, the
allocator — is billed to JIT_EXEC while no machine code is running. Validation: a tight
compiled loop reads correctly (ArithLoop 75%, FieldsRef 82.8% inside, the remainder being
process startup).

Block B's host side, by function, averaged over the 10 s blocks whose compiled-side rows are
VoxelShape/BlockStateBase:

| item | share of Block B wall |
|---|---|
| `str::contains` (`memchr` + `is_contained_in` + `next_match`) | ~9% |
| name-keyed lookup (`get_or_load`, SipHash, `field_key_get`, `super_chain`, `memcmp`) | ~9% |
| allocator (`mi_malloc_aligned`, `mi_free`, `Heap::gc`) | ~7% |
| dispatch host path (`jit_direct_invoke`, `jit_direct_probe`, `jit_call`, `lambda_fp`) | ~11% |
| interpreter opcodes reached from compiled callbacks (`ref_parts`, `invokevirtual`, `getstatic`, `instance_of`) | ~6% |
| `RtlQueryEnvironmentVariable` — an unmemoised `std::env::var_os` on the getfield path | ~1% |

**So `bench/ShapeOr.java`'s 75× is not a codegen gap.** It is the most host-call-dense workload
in the tree: 536 dynamic calls out of compiled code per `Shapes.or`, each paying per-call
bookkeeping that is O(string) and O(malloc). Its own header used to say "the cause is dispatch,
not arithmetic"; the correction is that it is neither — it is what the host does per dispatch.

Consequences worth carrying forward: a lever aimed at the value model or at Cranelift's output
addresses under a tenth of Block B, and any future reading of a JIT_EXEC percentage should be
cross-checked with `RAVA_PROFILE_PC` before it is called codegen.

`Done` cannot measure any of this — it starts at `Starting minecraft server version`, after
blocks A, B and C. Use `bench/boot_blockb_ab.ps1`, which measures to the `Environment:` line.

## The ring RE-DERIVES WORK — the largest lever found in this arc

The router DAG is tiny: **2,153 objects, 3,445 edges, 238 nodes shared between parents**. Minecraft's
own caching markers (`FlatCache`/`Cache2D`/`CacheOnce`, 29 `Marker` nodes) are **inert outside
`NoiseChunk`**, so each shared node is re-evaluated once per incoming edge. One ring task is 3,249
`Climate$Sampler.sample` × 56 `DensityFunction.compute` = 127,332 computes at recursion depth 6 —
and **of the 56 computes per sample only 15 are distinct; 41 (73%) are exact repeats.**

Measured in Rava on the real ring task (not a proxy): a shared-memo sampler gave 9,747 samples
2,135→708 ms (**3.0×**) and full `findBiomeHorizontal` 780→400 ms (**1.96×**), bit-exact over 500
positions. 92.6/1.96 ⇒ a ceiling of about **−45s on the Done window**. It is on the right side of
the transfer rule: it REMOVES work rather than duplicating a body.

Soundness is the whole difficulty, and a bit-exact gate does not establish it: the arena is a
MOVING collector (a stale address can be reused by a different object ⇒ false hit), and static
purity proves only that *this call* does not write, not that nobody mutates the receiver's
reachable graph between two calls.

**The ring is pure compiled-code throughput** — 97.1% JIT_EXEC, 1.4% dispatch, 0.6% native
bridges, **0% GC, one handle-heap allocation**. And **ChunkFill is not a proxy for it**: the ring
never evaluates `finalDensity` (depth 41), touching 96 of 241 tree positions.

## Repricing: a warm host fall costs ~99 ns, not ~1.2 µs

Admitting GC-leaf entries to the lambda PIC took directable lambda falls 1,411,982 → **5** (PIC
hits 70.5%→80.6%, host falls 4.10M→2.68M) and bought **2.3%** on ShapeOr. 1.41M falls ≈ 2.3%
prices a warm fall at **~99 ns** — 92% of them were already served by a warm `jit_direct_call`
cache, so a machine-code hit only deletes the callback boundary, which the PIC's own codegen tax
(+0.8%, measured inert) nearly cancels. **Any estimate of the form "N falls × 1.2 µs" overstates
by ~12×.** The capturing arm was priced and deliberately not built: 10.3 capture cells per call,
each needing a runtime test-and-select because `decode_arena_cell` discriminates on the low two
bits, plus a per-call bail — see `docs/lambda-machine-code-pic-blocker.md`.

mechanism works and is bit-exact (RingScan `3ed21b4965`, ChunkFill `8790f04ace726ecf`)
but the transitive effect proof admits NONE of the ring's hot path, so 14.3 M windows
opened for 97,484 stores and **0 hits**; interleaved real boot **wall +16.8%** (min-of-N
